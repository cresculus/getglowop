Fleet inventory is confidential customer data. GLOW Ops treats it that way: TLS from the endpoint, encryption at rest, one business ID per customer, and a dashboard that only loads businesses you are assigned to.

01 In transit

Data leaves the PC on HTTPS only

Collector and agent post inventory to ingest over TLS 1.2+. No cleartext upload path in production.

Transport

TLS to ingest

Inventory posts to https://ingest… only. HTTP is rejected. Modern ciphers; HSTS on the edge.

Auth

Enrollment key in the header

Bearer token proves which business may receive the device. The key never goes in the query string.

Least privilege

Inventory only

No keylogging, no mailbox scrape, no “power spy.” Hardware and health signals for the GLOW Op Report — that is the scope.

Local hardening

Spool ACLs

On-disk spool and config under ProgramData are locked to SYSTEM and Administrators while waiting for a successful upload.

02 At rest

Stored encrypted for the business partition

Production stores inventory in a tenant-scoped database and encrypted object storage — not a shared pile of files.

Database

Encrypted disks + CMK path

Primary store on encrypted volumes. Customer-managed keys (KMS / Key Vault) when the contract requires it. Backups follow the same policy.

Objects

Raw JSON and reports

Raw payloads and white-label PDFs live in encrypted buckets with public access blocked.

Secrets

Enrollment keys hashed

Mint once, show once. At rest we store a hash or a KMS-wrapped secret — not a plaintext kit in git.

Retention

Delete means purge

Offboarding a business includes deleting that partition’s rows and objects — not just hiding them in the UI.

03 Tenancy

ConnectWise-style business IDs

Same agent binary for every customer. Different business ID and enrollment key. Ingest trusts the key — not a forged claim in the JSON.

Device --Bearer enrollment key--> Ingest
Ingest --resolves--> businessId / dashboard / DB partition
Mismatch between claimed business and key --> 403

businessId

Company

Like a ConnectWise Company ID. Every device and report row belongs to one business.

siteId

Optional site

HQ, warehouse, clinic — optional location under that business.

enrollmentKey

Install secret

Routes the device into that business’s database. Acme’s kit never goes on Beta’s PCs.

deviceKey

Stable device id

Hash of manufacturer + serial (or machine GUID fallback). Upserts cleanly inside the business.

04 Who can see what

The database is only visible to who is assigned

Humans log in with an identity provider. The API loads their business assignments before any query runs.

  • MSP adminAll businesses under that MSP org.
  • MSP technicianOnly the businesses they are assigned to — not the whole book of business by default.
  • Customer admin / viewerTheir business only. Viewer is read-only.
  • Device / enrollmentWrite inventory to ingest. Cannot open the dashboard.
  • Platform break-glassGlowOps staff only, audited, time-bound.

Defense in depth: application filters and database row-level security on business_id. A buggy report query still cannot leak another tenant.

05 Deploy without mixing tenants

Intune, RMM, or Nerdio — per company

White-glove mints one client kit per business. Push that kit through the management plane that company already uses.

Intune

Win32 in their tenant

Package the kit, assign to that customer’s device groups only. Detection checks the business ID on disk.

RMM

Client script library

Paste the self-contained installer into that client’s script — never a global script shared across companies.

Nerdio

Scripted Action

Scope the action to that Nerdio customer or host pool. AVD hosts get the same enrollment binding.

Intune-first fleets

Graph connector

When Intune already has the inventory, prefer the cloud connector — no resident agent required.
